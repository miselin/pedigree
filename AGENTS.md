# Pedigree Agent Guide

## Source layout

- `docs/` — kernel and subsystem documentation
- `external/` — third-party dependencies and submodules
- `images/` — disk-image files and build scripts
- `scripts/` — development and QEMU helpers
- `src/buildutil/` — host-side build utilities and tests
- `src/modules/` — kernel modules, drivers, and subsystem layers
- `src/system/` — kernel proper
- `src/user/` — userspace applications and libraries
- `src/po/` — translations
- `build-etc/` - build system configuration and support files

## Building

- Use `uv` for Python scripts in this repository.
- `./easy_build_x64.sh` builds the amd64 kernel, userspace, and disk images.
- After the initial build, `cmake --build build` is usually the fastest incremental build path.
- `./verify.sh` builds host-runnable kernel components for supported native testing.

Reuse existing build directories and cross-compilers where practical. Prefer focused build targets during development rather than rebuilding the entire system after every small edit.

## Code style

- Follow `.clang-format` for C and C++.
- Format only changed lines; do not reformat unrelated code.
- Use `ruff` for Python.
- Add braces around single-line if, else-if, and else statements; these are ambiguous so `clang-format` will not fix this for you.
- Follow surrounding repository style where it is more specific than these rules.

## Verification

Use the narrowest existing mechanism that establishes confidence.

For kernel utilities that can run on the host, prefer the existing build-utility tests, benchmarker, or `verify.sh`.

For guest testing:

- Prefer `scripts/qemu --serial` for interactive work. It runs headless and connects the guest COM1-backed `/dev/ttyS0` terminal to the invoking shell.
- Use `scripts/run-qemu-iso.py` when a bounded, marker-based guest run is useful.
- Build a fresh ISO before treating guest serial output as evidence of the current source state.
- Distinguish host execution, compile-only checks, routing checks, and actual guest execution; they establish different things.

Add tests when they protect meaningful behaviour or regressions. Avoid creating new harnesses, scripts, or integration suites when existing mechanisms are sufficient.

## Concurrency and shared state

Pedigree's build and QEMU workflows contain shared mutable state.

- Avoid concurrent agents modifying or using the same build directory or writable disk image.
- Never rebuild or replace a backing image while a guest is using it.
- Use independent writable state for parallel QEMU guests.
- For concurrency-sensitive kernel changes, verify both single-CPU and SMP behaviour when that distinction is relevant.

Prefer project-level concurrency primitives when several subsystems already solve the same lifetime, synchronization, or reclamation problem. Do not build substantial one-off protocols inside a subsystem without checking whether the problem is already repeated elsewhere.

## Persistence testing

Runtime disk writes may be disabled in test builds.

- For tests that genuinely require persistence, verify `PEDIGREE_CRIPPLE_HDD=FALSE`.
- Use disposable writable disks for such tests.
- Restore any shared build configuration changed for persistence testing.
- A passing cache-only test does not establish disk writeback correctness.

Do not apply this ceremony to work that does not exercise persistent storage.

## Repository hygiene

- Prefer updating existing documentation over creating new reports or analysis files.
- Keep temporary logs, reproductions, generated reports, and debugging artifacts out of tracked source unless they have clear lasting value.
- Preserve unrelated edits.
- Keep patches focused on the requested work.

## Pull requests

Keep each PR centered on one coherent change. Summarize behaviour, relevant validation, and known limitations or deferred work.

When creating or updating a PR, apply exactly one provenance label:

- `ai-generated` — the majority of the PR's code or content was generated by AI.
- `human-generated` — the majority was written by a human, even if AI tools assisted.

Also apply at least one appropriate change-category label:

- `bug`
- `documentation`
- `enhancement`

Use multiple category labels only when the PR genuinely spans them. Do not add unrelated workflow labels unless explicitly requested.
